# 要件定義 rev.5

実装済みの内容に合わせた版。方式選択の根拠は [`phase0-findings.md`](phase0-findings.md) を参照。

rev.4 からの差分は **M3（判定を本物にした）**。§5 を新設し、FR-01 / FR-02 / NFR-07 / R-03 を更新した。

## 1. 前提

| | |
|---|---|
| 対象端末 | Pixel 9 Pro XL / 1344×2992 / 3.0x / 448×997dp |
| minSdk | 31 |
| 配布 | ADB サイドロード。Play ストアには出さない |
| 対象アプリ | YouTube（Shorts のみ）、X（アプリ全体） |
| 依存ライブラリ | **ゼロ**。永続化は SharedPreferences |

半径は**物理ピクセル**指定。σ の近似は `σ = 0.57735 × radius + 0.5`。

## 2. 確定した方式

| 項目 | 採用 |
|---|---|
| ブラー API | `Window#setBackgroundBlurRadius` |
| 実装形態 | 全画面 `Dialog` |
| ウィンドウ種別 | `TYPE_ACCESSIBILITY_OVERLAY` |
| ウィンドウ alpha | **1.0**（下げるとブラーが減衰する） |
| 背景ドローアブル | `#01000000` |
| 遷移 | **250ms のフェード** |
| 通知シェード | SystemUI 前面検出で**完全に解除** |

## 3. 半径の上限

実測の判読限界（Shorts 40 / X 16）を **1.5 倍**した値を上限にしている。
限界ちょうどだと「かろうじて読めてしまう」余地が残るため。

| アプリ | 判読限界（実測） | 採用する上限 |
|---|---:|---:|
| YouTube Shorts | 40 | **60** |
| X | 16 | **24** |

## 4. 消費量モデル

消費量 C は**アプリ間で共有**する。アプリごとに分けて持つと、
交互に使うことで永久に猶予帯へ留まれてしまうため（代償行動の封じ込め）。

一方、**到達時間と上限はアプリごとに持つ**。媒体によって「もう十分見た」と
感じる時間が違うため。

```
# 対象アプリが前面のとき、1 秒ごとに加算
C += 1

# 1 枚送りのスワイプ 1 回につき加算（既定 3 秒ぶん）
C += swipeWeight

# 対象外・通知シェード表示中・画面 OFF では減衰（半減期 90 分）
C *= 0.5 ^ (経過秒 / 5400)

# 毎日 04:00 に C = 0

# 猶予はアプリごとの到達時間に比例（つまみを増やさないため）
G[app] = T[app] × 0.30

# 強度 0〜1
p = 0                                   C ≤ G[app]
p = ((C − G[app]) / (T[app] − G[app]))^k  G[app] < C < T[app]
p = 1                                   C ≥ T[app]

# 半径
R = R_MAX[app] × p

既定: k = 2.0
     T = { YouTube: 600秒(10分), X: 420秒(7分) }   ※ 3〜10分で可変
     R_MAX = { YouTube: 60, X: 24 }
     swipeWeight = 3
```

減衰は**「読むときに経過時間ぶんまとめて適用する」**方式。
サービスが死んでも端末を再起動しても、離れていた時間が正しく反映される。

スワイプを時間より重く数えるのは、**高速に飛ばす消費**を捉えるため。
1 本を 3 秒でスワイプし続ける使い方は、同じ時間じっと見ているより消費として重い。

### 既定値でのふるまい

**YouTube**（到達 10 分 / 上限 60）

| 経過 | 半径 |
|---:|---:|
| 3分 | 0（猶予） |
| 5分 | 5 |
| 6分 | 11 |
| 7分 | 20 |
| 8分 | 31 |
| 10分 | 60 |

**X**（到達 7 分 / 上限 24）

| 経過 | 半径 |
|---:|---:|
| 2分6秒 | 0（猶予） |
| 4分 | 4 |
| 5分 | 8 |
| 6分 | 15 |
| 7分 | 24 |

σ は半径に線形なので体感の劣化は前半に集中する。
k = 1.0（線形）だと序盤で一気に潰れて後半は何も起きない。

スワイプぶんが乗るので、飛ばして見れば表の時刻より早く到達する。

## 5. 判定

**YouTube は Shorts を見ているときだけ対象**にする。通常の動画とフィードは数えない。

**X はアプリ全体を対象**にする。タイムラインも個別ポストも消費であることに
変わりはなく、無理に区別すると壊れやすい判定を増やすだけになるため。

### 二層にする

| 層 | 方法 | 強み | 弱み |
|---|---|---|---|
| 一次 | **1 枚送りのスクロール量** | ビュー ID に依存しない。YouTube の更新で壊れない | 1 本をじっと見ていると成立しない |
| 二次 | **ビュー ID** の有無 | 確実 | 更新で必ず壊れる |

```
inShorts = (ID が見つかった) || (最後の1枚送りから10秒以内)
```

どちらか一方でも成立すれば Shorts とみなす。**ID が腐っても一次判定だけで動く。**

一次は `TYPE_VIEW_SCROLLED` の `scrollDeltaY` を見る。Shorts は 1 スワイプで画面 1 枚ぶん
飛ぶので移動量が画面高に近い。通常のフィードは指の動いたぶんだけ連続的に動くので届かない。
閾値は**画面高の 70%**（Pixel 9 Pro XL で約 2094px）。

二次は 1 秒に 1 回だけ実行する。毎イベントでノードツリーを探すと重いため。

### 劣化を検知する

一次と二次が食い違った回数を数え、状態画面とログに「不一致 N 回」として出す。
**ID が腐り始めたことに気づくため**の仕組みで、増え始めたら `detection.json` を直す合図。

### 外部ファイル

ビュー ID・閾値・スワイプの重みは端末上の JSON で差し替えられる。**再ビルドが要らない。**

```
/sdcard/Android/data/dev.veil.blurprobe/files/detection.json
```

ファイルが無ければコード内の既定値を使う。壊れた JSON なら既定値に落ちる。

## 6. 手動解除

**1 日 1 回だけ**、消費量 C を 0 にリセットできる。

| 状況 | 動作 |
|---|---|
| 今日まだ使っていない | C を 0 に。「ぼかしをリセットしました。解除は1日1回のみです」 |
| 今日すでに使った | 何もしない。「本日の解除は使用済みです。あと◯時間◯分で回復します」 |

回復は 04:00（Veil の一日の区切り）。

C のリセットは強い救済なので回数を絞っている。**使ったこと自体が記録に残る**ので、
毎日使うようならペースが速すぎるという判断材料になる（R-02 の観測）。

操作経路は常駐通知とクイック設定タイルの 2 つ。

### 自動で外れる条件

手動解除とは別に、以下では半径が 0 になる。**いずれも C は保持する**ので、
対象に戻れば元の濃さから再開する。

| | |
|---|---|
| 対象アプリから離れた | 前面が変われば判定状態を捨てる |
| Shorts をやめた | 10 秒間 1 枚送りがなく、ID も見つからない |
| 通知シェードを引き下ろした | シェード自体が読めなくなるのを防ぐため |
| 画面 OFF | |
| 機能を停止中 | §7 |

## 7. 機能の入切

**止めるのは苦痛に、戻るのは楽に。** 非対称にしている。

| | 操作 |
|---|---|
| 停止 | ボタンを **3 分間押し続ける**。指を離すとやり直し |
| 再開 | タップ 1 回 |

**停止中も視聴時間の記録は続く。** 止めている間に何分見たのかが分からないと、
止めた効果そのものが測れなくなるため。

## 8. 記録

`UsageLog`。Room は使わず SharedPreferences に日別で持つ。
1 日 1 アプリあたり整数ひとつしか要らないため。

消費量 C とは別物。C は「今どれだけぼかすか」を決める**減衰する値**、
こちらは「実際に何分見たか」の**減衰しない記録**。

画面に出るもの:

```
今週      YouTube 3時間12分   X 48分
先週比    YouTube +18%   X −32%
合計      4時間0分（先週比 +6%）
累計      41時間20分
解除      3日連続で未使用
```

- **先週比**は「直近 7 日」対「その前の 7 日」。暦の週で切らないので週の途中でも意味がある
- **解除の連続未使用日数**は、Digital Wellbeing が持たないこのアプリ固有の信号
- 日別データは 120 日で自動的に古いものを捨てる。累計は捨てない

## 11. 権限

| 権限 | 付与方法 |
|---|---|
| AccessibilityService | 設定 → ユーザー補助（起動スイッチを兼ねる） |
| `canRetrieveWindowContent` | サービス設定で宣言。**ID の有無の照会にのみ使う** |
| `POST_NOTIFICATIONS` | アプリ内で要求 |
| 電池最適化の除外 | 設定から手動 |

`SYSTEM_ALERT_WINDOW` / `FOREGROUND_SERVICE` / `WRITE_SECURE_SETTINGS` は**不要**。

`canRetrieveWindowContent` は M3 で true にした。読める範囲が広がるのは事実なので、
**一次判定だけでも動く構成**にして、この権限への依存度を下げてある。

サービス設定 XML を変えたため、**更新後はユーザー補助を一度オフ→オンし直す必要がある。**

## 12. 懸念

| ID | 懸念 | 重大度 | 状態 |
|---|---|---|---|
| R-01 | 動画上でブラーが描画されない | 解消 | 実機で否定 |
| **R-02** | **慣化でぼかしが無視される** | **致命** | **最大の未解決リスク。**解除の使用頻度と先週比で観測する |
| R-03 | Shorts 判定が YouTube 更新で壊れる | 高 | 対応済。一次判定は ID 非依存、劣化は不一致カウンタで検知 |
| R-04 | 画面がぼけたまま復帰できない | 解消 | 通知・タイルで実証済 |
| R-05 | サービスが OS に停止される | 中 | 電池最適化の除外 |
| R-06 | 音声だけで消費が続く | 中 | 記録を見て判断 |
| R-07 | 代償行動（別アプリへ移動） | 中 | C をアプリ間で共有 |
| R-08 | Advanced Protection Mode との非互換 | 中 | 有効化されると描画ごと止まる |
| R-09 | GPU コストとバッテリー | 中 | カクつきなし。電池は自己運用で確認 |
| R-13 | シェード復帰時の 0.5 秒の遅れ | 軽微 | 250ms のフェードで許容と判断 |
| R-14 | 70% 閾値がフィードで誤爆する | 低 | 実機で誤爆なし。続けて観測 |
