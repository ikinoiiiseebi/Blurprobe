# 実装の状況

## 完了

### Phase 0 — 方式の検証

検証用アプリを 12 版重ねて、ブラーの描画方式を確定させた。
詳細は [`phase0-findings.md`](phase0-findings.md)。

### M1 — 消費量に応じたぼかし

| | |
|---|---|
| FR-02 | 対象アプリの滞在秒数を計測し、消費量 C に加算 |
| FR-03 | C → 強度 → アプリ別 `R_MAX` → 半径 |
| FR-06 | 対象外・画面 OFF で減衰（半減期 90 分）、04:00 リセット |

判定は仮実装。Shorts と通常の YouTube 動画を区別していなかった（M3 で解消）。

### M2 — 設定と記録

当初は Room で日次ログを持つ計画だったが、**Room は落とした。**
1 日 1 アプリあたり整数ひとつしか要らないので、SharedPreferences で足りる。

| | |
|---|---|
| FR-08 | 視聴時間の日別記録、先週比、累計 |
| FR-09 | ペースをアプリ別に調整（3〜10 分） |
| FR-11 | 3 分長押しでの機能停止 |
| FR-12 | 1 日 1 回の手動リセット |

**FR-10（週次の再調整通知）は削除。** 画面を開けば先週比が出るので不要になった。

### M3 — 判定を本物にする

仮判定を二層構造に置き換えた。詳細は [`requirements.md`](requirements.md) §5。

| | 内容 |
|---|---|
| FR-01 | 一次＝1 枚送りのスクロール量（画面高の 70%）、二次＝ビュー ID |
| FR-02 | スワイプ計数（1 回 = 3 秒ぶん） |
| FR-13 | 判定の不一致を数えて表示 |
| NFR-07 | ビュー ID・閾値・重みを `detection.json` に分離 |

**受け入れ条件の結果**

| 条件 | 結果 |
|---|---|
| Shorts と通常動画を切り替えて誤判定 0 | 通った |
| フィードのスクロールで誤爆しない | 通った |
| 不一致が出ない（＝同梱 ID が生きている） | 出ていない |
| ~~X のタイムラインと個別ポストを区別~~ | **取り下げ。** どちらも消費であり、判定を増やすと壊れやすくなるだけ |

**R-03 は解消とみなす。** ID が腐っても一次判定だけで動き、
腐ったこと自体は不一致カウンタで気づける。ID は再ビルドなしで差し替えられる。

## 自己運用で見ること

ここからが本番。実装と並行ではなく、**日常的に使いながら 2 週間観測する。**

| 見るもの | 判断 |
|---|---|
| 先週比が減っているか | 効いている／いない |
| 手動リセットの使用頻度 | 毎日使うならペースが速すぎる |
| 同じ段階での滞在時間 | 延びていれば**慣化（R-02）が起きている** |
| 不一致カウンタ | 増え始めたら `detection.json` を直す |
| 電池の減り | 常用に耐えるか（V-04 の繰り越し） |

**R-02 が最大の未解決リスク。** 技術の問題は片付いているので、
残っているのは「実際に効くのか」という問題だけ。

## 保留

先回りして実装しない。運用結果を見てから判断する。

| | 判断材料 |
|---|---|
| 音量への介入（R-06） | 最大到達後の滞在時間が長ければ、音声だけで消費が続いている |
| ペースの作り直し | 手動リセットの使用頻度 |
| スワイプの重み（既定 3 秒） | 飛ばし見が抑えられているか |
| 「消費したサムネイルが積み上がる」表現 | 当初案。ブラーで十分なら不要 |
| 対象アプリの追加 | まず 2 つで慣化が防げるかを見る |

## 訂正の記録

過程で誤っていた見込みを残しておく。同じ間違いを繰り返さないため。

| 誤り | 実際 |
|---|---|
| 「R-01（動画上でブラーが出ない）が最大リスク」 | 起きなかった。トンネリングは Android TV 向け機能 |
| 「権限ダイアログや電源メニューを覆う」 | 起きなかった。タップジャッキング対策で自動的に隠れる |
| 「8 分で明らかにぼけている」（M1 の受入条件） | 当初の T=20 分では 8 分で半径 3。カーブの計算を怠っていた |
| 「M2 には Room が要る」 | 要らなかった。SharedPreferences で足りる |
| 「X のタイムラインと個別ポストを区別する」（M3 の受入条件） | 区別する意味がなかった。どちらも消費 |

### 手順の失敗

`Curve.p()` に引数を足したとき、`status()` の呼び出しを直し忘れたまま
次の版を作り、**同じビルドエラーを 3 回再発させた。**
原因は、手元で直した内容が次の版に反映されない受け渡し方だったこと。

M3 のコミット後にリポジトリを直接読めるようにして、この経路を断った。
